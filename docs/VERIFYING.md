# Verifying a change

Every PR is verified the same way, whether a person or an agent wrote it:

1. **`just verify`** runs what CI runs, checks your commits and your PR, and
   prints a receipt.
2. **A live test** shows the change working in a real Home Assistant. What it
   must show depends on the parts of the code the change touches, and
   `just verify` lists it for you.
3. **The PR description** carries both, under `## How I tested this`, plus an
   `## AI use` line. The `PR Metadata` check enforces this.

Everyone runs the same tool versions (`uv.lock`, uv's managed Python), so
`just verify` gives the same answer on any machine, and the same answer CI
gives.

## `just verify`

Run it on your branch, with everything committed, before you open a PR and
again before you ask for review:

```bash
just verify          # everything, ends with the receipt (about two minutes)
just verify branch   # only the commit and PR checks, in seconds
just verify areas    # what a change to each part of the repo must show
```

| Line | Checks | Fix |
|------|--------|-----|
| `lock` | `uv.lock` matches `pyproject.toml` | `uv lock` |
| `lint` | ruff check and ruff format | `just fix` |
| `types` | mypy, strict | fix the types, never `# type: ignore` |
| `tests` | integration tests, 80% coverage floor | |
| `library` | aionanit tests | |
| `card` | the committed card bundle matches `frontend/src` (when the card changed) | `just card` |
| `protobuf` | generated code matches the `.proto` (when it changed, with protoc 29.5) | regenerate |
| `tree` | nothing uncommitted, so the receipt describes what you push | commit |
| `signed` | every commit on the branch is signed | [Signed commits](../CONTRIBUTING.md#signed-commits) |
| `credit` | no AI co-author trailers or "generated with" lines | reword the commit |
| `messages` | conventional commit subjects (a warning: only the PR title reaches `main`) | |
| `pr` | the open PR's title, Changelog, testing and AI use sections | edit the description |

Each line says `pass`, `fail`, `warn`, `skip` (not needed for this change)
or `ci` (this machine can't run it, CI does). Hassfest and the workflow
linters only run in CI. A `fail` makes the result `fail`, and the output
ends with how to fix each problem.

The receipt is the fenced block that starts with `ha-nanit verify <commit>`.
Paste it into the PR unchanged. `PR Metadata` checks that its commit is in the
PR and that it says `result: pass`. It warns, without failing, when the
receipt is for an older commit of the PR. Run `just verify` again before you
ask for review, so reviewers see the receipt for what they review.

## The live test

Tests prove the code does what the tests say. A live test proves it does what
users need, on the hardware they have. Write it under `Live test:` in the PR:
where you ran it (`just dev` or your own Home Assistant, and its version), the
device and firmware, what you did and what you saw. Add screenshots and log
lines where they help.

What it must show depends on the areas the change touches. `just verify` and
the `PR Metadata` job summary list them for each PR. "Needs" says what the
test takes: `account` is a Nanit login, `camera` a camera, `speaker` a Sound
& Light machine.

| Area | Needs | Live test must show |
|------|-------|---------------------|
| Lovelace card (`card`) | account | Screenshots of the card before and after in a dev Home Assistant, in a light and a dark theme, and no new errors in the browser console. |
| Setup and options forms (`config-flow`) | account | Go through each changed step (add, MFA, reauth, options, repair) in a dev Home Assistant, with a screenshot of each changed form. |
| Setup, upgrade and migration (`setup`) | account | Upgrade from the latest release with an existing entry: it loads, entities keep their ids, and the log shows no new errors. Then a fresh install. |
| Entities and their states (`entities`) | camera | The affected entities in a dev Home Assistant with their states, and each changed control used once. A changed unique id needs its migration shown too. |
| Live video (`streaming`) | camera | Watch the live view in a browser for at least five minutes on each route the change affects (local, cloud), with the log lines of any route change. Name the camera model and firmware. |
| Camera connection and login (`connection`) | camera | The scenarios from docs/CONNECTION_RELIABILITY.md that the change affects (network drop, Home Assistant restart, token refresh), each with the log showing the recovery. Name the camera model and firmware. |
| Sound & Light machine (`sound-light`) | speaker | Run it against a real Sound & Light machine (name its firmware) and confirm each AGENTS.md invariant the change touches still holds. |
| Logs, diagnostics and names (`privacy`) | account | Download diagnostics and a debug log from a dev Home Assistant and confirm no token, password, email or stream URL appears in them. |
| Protobuf messages (`protobuf`) | none | None beyond the areas of the code that uses them. Regenerate with protoc 29.5, never by hand. |
| Dependencies (`dependencies`) | none | A supply chain review of each added or bumped package, written in the PR (docs/SECURITY_AUDIT_CHECKLIST.md section 10). |
| CI, releases and dev tools (`tooling`) | none | How the changed workflow or tool was run: a link to the run, or the command and its output. |
| Agent rules (`agent-rules`) | none | None. The owner reviews and approves the diff itself. |
| Documentation (`docs`) | none | Read the rendered page on GitHub and check its links. |
| Tests only (`tests`) | none | None. Say which tests would fail without the change. |
| Other aionanit code (`library`) | camera | What was run against a real camera, or why the library tests cover it. |
| Other integration code (`integration`) | account | What was run in a dev Home Assistant to see the change work. |

The files behind each area are in
[`tools/verify-areas.toml`](../tools/verify-areas.toml). A file in no area
shows up as such in `just verify`. Add it to the area it belongs to in the
same PR.

**If you can't test live** (no camera, no Docker, an agent in a sandbox),
write `not tested live` and why. Never describe a test you didn't run. A
maintainer with the hardware tests it before merging, so the PR may wait for
them.

## What CI checks

| Check | What | Required |
|-------|------|----------|
| `CI OK` | lint, types, both test suites, card and protobuf drift, workflow lint, hassfest | yes |
| `PR Metadata` | conventional title, `## Changelog`, `## How I tested this` with a filled-in live test and a passing receipt from this PR, `## AI use`, every commit verified by GitHub, no AI co-author trailers | yes |

PRs from bots (Dependabot) skip the testing and AI use sections. Their
commits still have to be verified. `PR Metadata` runs the checker from the
PR's base branch, so a PR that changes `tools/verify.py` is checked by the
rules it would replace.

## Git hooks

`just setup` installs three git hooks that run the same checks at the
moment they apply:

- **pre-commit**: ruff fixes and formats the staged Python files.
- **commit-msg**: a conventional subject, and no AI co-author trailer.
- **pre-push**: every commit you push is signed.

Never skip them with `--no-verify`. A hook that fails tells you how to fix
the problem.

## For reviewers

- Read the live test against the area table. A missing area, a vague "works
  for me", or a live test the hardware couldn't have run is a reason to ask
  for more.
- `PR Metadata` already proves the receipt is from this PR and that every
  commit is verified. CI proves the checks pass on the head commit.
- Rerun `just verify` on the branch only for authors with merged PRs here. A
  newcomer's tests run as you, with your GitHub token in reach (see the
  `review-prs` skill).
